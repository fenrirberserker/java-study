## Java Fundamentals (condensed, cross-checked against standard knowledge)

- Java began as "Oak" (1991-1995, James Gosling and team at Sun Microsystems), originally targeting embedded consumer electronics (set-top boxes, appliances) that needed one program to run across many different CPU architectures — not originally designed for the Internet. The architecture-neutral bytecode model is a direct consequence of that original embedded-portability goal.
- Java syntax derives from C; its object-oriented model derives from C++, but Java is neither upward- nor downward-compatible with C++ — it is a new language, not a C++ variant.
- Bytecode (`.class` files) is not machine code — it's an intermediate, architecture-neutral instruction set interpreted (and Just-In-Time, or JIT, compiled piece-by-piece on demand) by the Java Virtual Machine (JVM). This is the mechanism behind "write once, run anywhere": only the JVM needs a platform-specific implementation, not each application.
- Four historical Java program categories worth knowing the vocabulary for even though most (applets in particular) are now obsolete/removed from modern JVMs: standalone applications, applets (browser-embedded, deprecated and removed from modern Java/browsers), web applications (servlets/JavaServer Pages, or JSP), and distributed applications (historically via Remote Method Invocation, or RMI).
- Java deliberately omits several C++ features to reduce ambiguity and bug surface: no multiple inheritance of classes, no global variables, no raw pointers/pointer arithmetic, no operator overloading. Each omission is framed as a source of common C/C++ bugs that Java's design intentionally engineers away — a good one-line justification to have ready if asked "why does Java not support X" in an interview.

## Exception Handling Q&A (the most substantively useful sampled section)

- **Hierarchy**: `Throwable` is the root, with two direct subclasses: `Error` (unrecoverable, out-of-scope-of-application conditions like a JVM crash or `OutOfMemoryError` — not meant to be caught/handled) and `Exception` (recoverable conditions). `Exception` splits further into **checked exceptions** (must be declared or caught, e.g., `FileNotFoundException` — conditions a well-written program can anticipate and recover from) and **unchecked/runtime exceptions** (subclasses of `RuntimeException`, e.g., `ArrayIndexOutOfBoundsException`, `NullPointerException` — generally symptoms of a programming mistake, not an anticipated recoverable condition).
- **Key `Throwable` methods**: `getMessage()`, `getLocalizedMessage()` (override point for locale-specific messages), `getCause()` (returns the wrapped originating exception, or `null`), `toString()`, `printStackTrace()`.
- **Java 7 multi-catch**: `catch (IOException | SQLException | Exception ex) { ... }` — collapses duplicate handler code for exceptions that should be handled identically, instead of repeating the same catch-block body per exception type.
- **Try-with-resources** (Java 7 Automatic Resource Management, or ARM): declaring a resource in the `try(...)` clause guarantees it is closed automatically when the block exits, eliminating the classic bug pattern of a `finally` block that a developer forgot to write (or wrote incorrectly), which silently exhausts resources like file handles or database connections over time.
- **`throw` vs. `throws`**: `throws` is part of a method signature declaring which checked exceptions may propagate out of it; `throw` is the statement that actually raises/hands off a specific exception instance at runtime.
- **Custom exceptions**: extend `Exception` or one of its subclasses; add fields (e.g., an application-specific error code) and a constructor that forwards a message to `super()`.
- **`final` vs. `finally` vs. `finalize()`** (a perennial interview trivia question): `final` and `finally` are keywords (`final` — no reassignment/no override/no subclassing depending on target; `finally` — a try-block clause that always executes, typically used to release resources even when try-with-resources isn't used); `finalize()` is a method invoked by the garbage collector before object destruction. Of the three, only `finally` is actually part of exception-handling control flow — `finalize()` is deprecated in modern Java (removed as a reliable cleanup mechanism in favor of `try-with-resources` and `Cleaner`) and should not be relied upon for resource cleanup.
- **Exception-handling best practices** the book calls out explicitly: throw specific exception types (not a bare `Exception`) for easier debugging; fail fast (throw as early as the invalid state is detected); catch late (let the caller — who has more context about how to recover — handle it, rather than swallowing it deep in a low-level method); never leave an empty catch block (at minimum, log it — a silently swallowed exception is one of the hardest classes of bug to diagnose later); prefer a single custom exception type per logical error category so callers can catch meaningfully.

## Takeaways for a Senior Backend Java Developer

- This book's unique value versus the other two Interviews-folder books is volume of rapid-fire Q&A phrasing, particularly around exception handling — useful as a quick self-quiz before an interview, not as a primary learning source.
