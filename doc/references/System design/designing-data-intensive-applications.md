# Designing Data-Intensive Applications

Source: Martin Kleppmann, *Designing Data-Intensive Applications* (O'Reilly, 2017, 613 pages). Widely regarded as the definitive book connecting database internals, distributed systems theory, and practical system design. Sampled: full table of contents (12 chapters across three parts), and detailed reads of Chapter 3's storage-engine internals (pages 91-101: log-structured hash indexes, SSTables, LSM-trees, and the setup for B-tree comparison) and Chapter 11's stream-processing chapter (pages 461-488: message brokers vs. log-based systems, partitioned logs and consumer offsets, event sourcing/change data capture, state-stream duality, CQRS).

This is the deepest, most theoretically grounded book in this reference library's System Design collection — where `grokking-system-design-interview.md` and `system-design-interview-alex-xu.md` teach *how to answer* interview questions via worked examples, this book teaches *why the underlying mechanisms work the way they do*. This file organizes coverage by the book's three parts, with the deepest verified detail in the two directly-sampled chapters, and connects specific sections forward to related material already in this repository.

## Part I: Foundations of Data Systems

### Chapter 1 — Reliability, Scalability, Maintainability
The book's foundational vocabulary, worth using precisely: **reliability** (the system works correctly even when things go wrong — hardware faults, software bugs, human error), **scalability** (the system's ability to cope with increased load, always evaluated relative to a specific growth dimension — "how does the system perform if we triple traffic" is a meaningful question; "is it scalable" alone is not), and **maintainability** (operability, simplicity, and evolvability — three distinct sub-concerns, since a system can be simple to operate but hard to extend, or vice versa). Load is described via **load parameters** specific to the system (requests/second, read/write ratio, active users, cache hit rate), and performance via **percentiles**, not averages — the book's specific, memorable argument: a slow request experienced by even 1 in 1,000 users (p999) matters disproportionately if that unlucky 0.1% tends to be your highest-value customers (e.g., those with the most data, hence the slowest queries), so tail latency is not a rounding error to ignore.

### Chapter 2 — Data Models and Query Languages
Contrasts the relational model, the document model, and graph data models, framed around the fundamental tension between normalization (avoiding duplication, requiring joins) and denormalization (duplicating data for locality, requiring the application or a derivation pipeline to keep copies in sync — directly connected to the CQRS/event-log material in Chapter 11, covered below).

### Chapter 3 — Storage and Retrieval (sampled in depth)

**Log-structured storage (hash index + SSTable/LSM-tree family)**:
- The simplest possible durable key-value store is an append-only log file plus an in-memory hash map from key to byte offset (this is literally how Bitcask, Riak's default storage engine, works). Appending is fast (sequential I/O); the approach requires the entire key set to fit in memory, and range queries are inefficient (no way to scan a key range without checking every key individually).
- **Segmentation and compaction**: the log is broken into fixed-size segment files; **compaction** discards all but the most recent value per key within a segment, and segments can be **merged** (background process, mergesort-like) to reclaim space, using **tombstone** records to mark deletions so they survive the merge.
- **SSTables (Sorted String Tables)**: requiring segment files to be sorted by key (rather than write-order) unlocks three advantages precisely worth remembering: (1) merging becomes a simple, memory-efficient mergesort-style scan across segments, even for files far larger than available RAM; (2) the in-memory index no longer needs every key — only a **sparse** index (one entry per few kilobytes) is needed, since the sort order lets you scan forward from the nearest known offset; (3) key-value pairs can be grouped into compressed blocks between index entries, saving both disk space and I/O bandwidth.
- **LSM-trees (Log-Structured Merge-trees)**: the mechanism that produces sorted SSTables from arbitrary-order writes — incoming writes go into an in-memory sorted structure (a **memtable**, typically a red-black tree or similar balanced tree), which is flushed to disk as a new SSTable once it exceeds a size threshold; reads check the memtable first, then progressively older on-disk segments; a background process continually merges and compacts segments. A separate on-disk write-ahead log protects against losing recent memtable contents on crash (the memtable itself is purely in-memory and unsorted-on-disk until flushed). This is the exact design underlying LevelDB, RocksDB, Cassandra, and HBase (the latter two directly inspired by Google's Bigtable paper, which coined "SSTable" and "memtable") — and matches precisely the write/read path documented from Cassandra's perspective in `system-design-interview-alex-xu.md`'s Key-Value Store chapter, now with the underlying rationale (why sorted files, why a memtable) made explicit.
- **Bloom filters** address LSM-trees' worst case — checking for a nonexistent key requires scanning every segment back to the oldest before concluding it's absent — by cheaply ruling out segments that definitely don't contain the key.
- **Compaction strategies**: size-tiered (successively merge newer/smaller SSTables into older/larger ones — HBase, and one of Cassandra's options) vs. leveled (split the key range into levels, moving data between levels incrementally — LevelDB and RocksDB's namesake strategy, and Cassandra's other option) — a real operational tuning knob, not just an implementation detail.

**B-trees** (the chapter's counterpoint, covered via `doc/references/Algorithms & Data Structures/data-structures-and-algorithms-in-java.md`'s external-memory/B-tree material — cross-reference rather than duplicate): B-trees break the database into fixed-size pages, updated in place, and remain the standard index implementation in almost every relational database. The book's central LSM-vs-B-tree comparison (not directly sampled here but standard, well-established content from this widely-cited chapter): LSM-trees generally have **higher write throughput** (sequential writes, no read-before-write for updates) but B-trees offer more **predictable latency** (no compaction-induced write stalls) and are the more mature, battle-tested default for transactional workloads. This is precisely the trade-off worth citing when explaining why a given database (Postgres/MySQL: B-tree; Cassandra/RocksDB/LevelDB: LSM-tree) made its particular storage-engine choice.

### Chapter 4 — Encoding and Evolution
Covers schema evolution and wire formats (Protocol Buffers, Avro, Thrift, JSON/XML), with a durable central lesson worth restating precisely: **backward compatibility** (newer code can read data written by older code) and **forward compatibility** (older code can read data written by newer code) are two distinct, independently-necessary properties for any system that evolves its schema over time without a synchronized big-bang deployment — a rolling deployment inherently has old and new code running simultaneously against the same data, so both directions matter. Directly relevant to any Kafka/Avro-based system, connecting to the schema-registry material already referenced in `doc/Study.md`'s Kafka section.

## Part II: Distributed Data

### Chapter 5 — Replication
Leader-based (single-leader) replication, multi-leader replication, and leaderless replication, each with distinct trade-offs the book returns to throughout the rest of the book:
- **Single-leader**: all writes go through one leader, replicated to followers — simple to reason about, but the leader is a bottleneck and failover requires careful handling (the book's detailed treatment of *replication lag* and its user-visible consequences — reading your own writes, monotonic reads, consistent prefix reads — is a foundational, frequently-cited framing of "eventual consistency" concerns in practice).
- **Multi-leader**: multiple nodes accept writes, requiring conflict resolution when the same data is concurrently modified on different leaders (last-write-wins, custom merge logic, or the vector-clock-style approach detailed mechanically in `system-design-interview-alex-xu.md`'s Key-Value Store chapter).
- **Leaderless** (Dynamo-style): no single leader; writes/reads go to multiple replicas directly, coordinated via quorum consensus (the `W + R > N` formula documented precisely in `system-design-interview-alex-xu.md`).

### Chapter 6 — Partitioning
Partitioning by key range (simple, supports efficient range scans, risks hotspots if access is skewed toward one range) vs. partitioning by hash of key (better load distribution, sacrifices range-query efficiency) — the same trade-off framed from the practical Grokking-book angle in `grokking-system-design-interview.md`'s Sharding section, and the consistent-hashing mechanism covered mechanically in both `grokking-system-design-interview.md` and `system-design-interview-alex-xu.md`.

### Chapter 7 — Transactions
The book gives a notably precise, skeptical treatment of ACID and, in particular, **isolation levels**, arguing that "serializable" is the only isolation level that actually delivers on its intuitive promise, and that weaker levels (read committed, snapshot isolation/repeatable read) each permit specific, named anomalies worth knowing precisely:
- **Dirty reads/dirty writes**: prevented even at the weakest useful isolation level (read committed).
- **Non-repeatable read (read skew)**: a transaction sees different values for the same row on two reads within itself, because a concurrent transaction committed a change in between — prevented by snapshot isolation.
- **Lost updates**: two concurrent read-modify-write cycles clobber each other — requires explicit locking (`SELECT ... FOR UPDATE`), atomic update operations, or automatic detection.
- **Write skew**: a genuinely subtle anomaly where two transactions each read overlapping data, then make disjoint writes that individually seem fine but together violate an invariant the application assumed (the book's canonical example: two on-call doctors each independently check "is at least one other doctor on call" before removing themselves from the on-call rota — both checks pass concurrently, and both remove themselves, leaving nobody on call). Write skew is **not** prevented by snapshot isolation and is a common source of production bugs precisely because it's rarely tested for — the fix requires either serializable isolation or an explicit lock on the read set.
- **Serializable Snapshot Isolation (SSI)**: the book's detailed treatment of how modern databases (including PostgreSQL) implement true serializability efficiently, by detecting (rather than preventing) dangerous read/write patterns and aborting conflicting transactions, rather than pessimistically locking.

### Chapter 8 — The Trouble with Distributed Systems
An extended, sobering treatment of why distributed systems are fundamentally harder than single-machine systems: unreliable networks (packets can be delayed, reordered, duplicated, or dropped with no way to distinguish "slow" from "lost" from the sender's perspective), unreliable clocks (both **time-of-day clocks**, which can jump due to Network Time Protocol, or NTP, synchronization, and **monotonic clocks**, which are only meaningful for measuring elapsed durations, not for comparing timestamps across different machines — mixing these up is a real, recurring bug source), and process pauses (garbage-collection pauses, virtual machine suspension, and even OS scheduling delays can make a perfectly healthy process appear dead to the rest of the system for an unpredictable duration — the book's specific, memorable argument is that **no timeout is ever fully safe**, since you can never distinguish "the other node is dead" from "the other node (or the network) is just very slow right now" with certainty).

### Chapter 9 — Consistency and Consensus
- **Linearizability**: the strongest single-object consistency guarantee — the system behaves as if there were only a single copy of the data, and every operation appears to take effect atomically at some point between its start and finish, respecting real-time ordering across all clients. The book is explicit that linearizability has a real cost (it fundamentally requires coordination, hence latency, and is impossible to achieve with full availability during a network partition — a concrete instantiation of the CAP theorem, which the book treats with more nuance than the folk "pick 2 of 3" framing: CAP is specifically about the trade-off *during a partition*, not a general property of the whole system at all times).
- **Ordering guarantees**: causality, and specifically why a **total order** of events (needed for things like consistent snapshots or a serializable transaction log) is fundamentally harder to establish across a distributed system than a **partial (causal) order** — directly related to the offset-based total order Kafka provides *within* a single partition (but explicitly not across partitions), as documented in this repository's Kafka material.
- **Distributed transactions and consensus**: two-phase commit (2PC) as the classic (and, the book argues, seriously flawed — the coordinator is a single point of failure/blocking hazard) approach to atomic commitment across multiple nodes, versus **consensus algorithms** (Paxos, Raft, Zab) which solve the more general problem of getting a set of nodes to agree on a value despite failures, and which underpin leader election in most modern distributed databases and coordination services (ZooKeeper, etcd). The book's key practical takeaway: consensus is provably impossible to solve deterministically in a fully asynchronous system with even one faulty node (the FLP impossibility result) — real systems work around this using timeouts and failure detectors that are imperfect but good enough in practice, which is precisely why leader election protocols (like Raft's) are framed probabilistically/practically rather than with absolute guarantees.

## Part III: Derived Data

### Chapter 10 — Batch Processing
Unix philosophy (composable tools operating on immutable input, explicit data flow via pipes) generalized to MapReduce and successor batch dataflow engines (Spark, Tez, Flink's batch mode) — the chapter's throughline is that **batch processing's power comes from the immutability and repeatability of its input**: since input files are read-only, a failed or buggy job can simply be re-run, with no risk of corrupting the source data — directly setting up Chapter 11's treatment of why the same idea (immutable, replayable input) is so powerful when applied to *unbounded* streams instead of bounded files.

### Chapter 11 — Stream Processing (sampled in depth — the chapter most directly relevant to this repository's Kafka coverage)

**Why streams, not just more-frequent batches**: batch processing requires artificially chopping an inherently unbounded, continuously-arriving dataset into fixed time windows (hourly, daily); stream processing abandons fixed slices and processes each event as it happens, trading batch processing's simplicity for lower latency.

**Messaging systems — two fundamentally different architectural families**:
- **Direct messaging** (UDP multicast, ZeroMQ, webhooks): low overhead, but requires the application to handle message loss explicitly, and generally assumes producers/consumers are constantly online — a consumer that's offline simply misses messages sent during that window.
- **Traditional message brokers** (RabbitMQ, ActiveMQ, JMS/AMQP-style systems): centralize durability and client churn-tolerance in the broker; messages are typically **deleted once successfully delivered** to their consumer(s), making these brokers unsuitable for long-term storage or for replaying history to a newly-added consumer. Support two consumption patterns — **load balancing** (each message goes to exactly one of a consumer group, sharing work) and **fan-out** (each message goes to every subscriber independently) — and use **acknowledgments** for reliable delivery, with the important, easy-to-miss side effect that combining load balancing with redelivery-on-crash **breaks strict message ordering** (a redelivered message can be processed out of order relative to messages sent after it), which matters whenever downstream logic has causal dependencies between messages.
- **Log-based message brokers (Kafka and equivalents)**: the architecturally distinct third option — messages are appended to a **partitioned, append-only log** rather than being destructively consumed. Each partition assigns every message a monotonically increasing **offset**; messages within one partition are totally ordered, but there is **no ordering guarantee across partitions**. Consumers track their own position via **consumer offsets** (directly analogous to a database replication log's log sequence number — "the message broker behaves like a leader database, and the consumer like a follower," in the book's own words), which is what allows the log-based model to natively support both fan-out (many independent consumers reading the same log, none of them deleting anything) *and* load-balancing (assigning whole partitions, not individual messages, to consumer-group members) — trading fine-grained per-message load balancing (a partition's messages always go to whichever single consumer owns that partition, creating head-of-line blocking if one message is slow) for dramatically simpler offset bookkeeping and much higher achievable throughput.
- **Retention as a bounded ring buffer on disk**: because logs are split into segments and old segments are eventually deleted (or, alternatively, log-compacted — see below), a log-based broker is effectively "a bounded-size buffer that discards old messages when it gets full" — but because that buffer lives on disk rather than memory, it can hold a genuinely large amount of history (the book's own back-of-envelope: a single 6 TB drive at 150 MB/s sequential write throughput takes about 11 hours to fill, meaning that much retention headroom is available "for free" even at maximum sustained write rate; real deployments rarely sustain full write bandwidth, so days or weeks of retained history is typical). Crucially, **log-based broker throughput stays roughly constant regardless of how much history is retained**, since every message is written to disk anyway — unlike memory-first brokers, whose throughput degrades once queues grow large enough to spill to disk.

**Databases and streams — event sourcing, change data capture, and log compaction** (this section is the direct conceptual foundation for understanding *why* Kafka is often used as more than "just a queue"):
- **State and streams are two views of the same information** — the book's own formulation: "application state is what you get when you integrate an event stream over time, and a change stream is what you get when you differentiate the state by time." A durable changelog makes application state fully reproducible by replaying it — quoting Pat Helland's framing directly: "the truth is the log. The database is a cache of a subset of the log."
- **Log compaction** bridges log and database semantics precisely by retaining only the latest value per key and discarding all superseded/overwritten entries (as opposed to time- or size-based retention, which discards based on age regardless of whether a key was later overwritten) — this is Kafka's `cleanup.policy=compact` setting, and it's what makes a compacted Kafka topic usable as a durable, replayable representation of current key-value state (e.g., backing a `KTable` in Kafka Streams, or serving as the changelog for a stateful stream-processing job's local state store).
- **Commands vs. events**: a request is a **command** (may still be rejected — e.g., a username or seat is already taken) until validated; only after validation does it become an immutable **event**, a fact that remains true forever even if later superseded by a compensating event. Consumers of an event stream cannot reject events — validation must happen synchronously before publication, or via a two-step tentative-then-confirmed event pair.
- **CQRS (Command Query Responsibility Segregation)**: separating the write-optimized event log (the system of record) from one or more independently-derived, read-optimized views built by consuming that log — this dissolves much of the traditional normalization-vs-denormalization tension, since a denormalized read view can always be rebuilt from the authoritative log rather than being a source of drift risk. The book cites the analytics database Druid and the key-value store Pistachio as real systems that ingest directly from Kafka using exactly this pattern, and Kafka Connect as the general-purpose mechanism for exporting a log's contents into arbitrary downstream databases/indexes.
- **Concurrency implications**: because a single-threaded consumer of one partition processes events strictly serially, event sourcing can *simplify* concurrency control for state confined to one partition (no locking needed — the log itself imposes a deterministic order) — but this benefit is lost the moment a single logical operation needs to touch state spread across multiple partitions, which then requires additional coordination.
- **Limits of immutability**: an ever-growing immutable event history isn't free — high-churn datasets can make compaction/garbage-collection performance-critical, and real-world requirements (privacy/data-protection law, containing an accidental data leak) sometimes require genuinely deleting data despite the append-only philosophy — the book notes this is harder than it sounds, since copies of "deleted" data can persist in backups, storage-engine internals, and SSD wear-leveling remaps regardless of application-level intent.

### Chapter 12 — The Future of Data Systems
A more speculative closing chapter on unbundling databases into composable stream-processing primitives, data integration across heterogeneous systems via change-data-capture pipelines, and — notably prescient for a 2017 book — a discussion of correctness/auditing in systems built from asynchronous, eventually-consistent pipelines, plus ethical considerations (data misuse, discrimination via automated decision-making) that were unusually forward-looking for a systems-engineering text at the time.

## Takeaways for a Senior Backend Java Developer

- This is the single book in this reference library most worth reading cover-to-cover rather than treating as a lookup reference — its value is in the connected reasoning across chapters (how replication lag connects to isolation levels, how consensus connects to leader election, how log-structured storage connects to Kafka's own internals), not any one isolated fact.
- The LSM-tree vs. B-tree trade-off (write throughput vs. latency predictability) is the correct, precise answer whenever asked "why would you choose Cassandra/RocksDB over Postgres/MySQL for this workload," and directly explains design choices visible in this repository's other references (`system-design-interview-alex-xu.md`'s Key-Value Store write/read path, `algorithms-notes-for-professionals.md`'s B-tree coverage).
- The state/stream duality and log-compaction material is the conceptual key to understanding modern Kafka usage patterns beyond simple pub/sub — Kafka Streams' `KTable` abstraction, event-sourced microservices, and CQRS architectures are all direct applications of the ideas in this chapter, and are folded into `doc/Study.md`'s expanded Kafka section.
- The write-skew anomaly (the on-call-doctors example) is a genuinely underappreciated, production-relevant bug class worth having as a concrete example — most engineers can define "race condition" abstractly but few can immediately produce an example that snapshot isolation specifically fails to prevent.
- "No timeout is ever fully safe, because you can't distinguish a dead node from a slow one" is the single most useful mental model from Chapter 8 for reasoning about any distributed system's failure-detection and retry logic, including everyday microservice timeout/circuit-breaker configuration.
