# Software Architecture Patterns

Source: Mark Richards, *Software Architecture Patterns* (O'Reilly report, 2015, 55 pages). Read in full. Covers five major application-level architecture patterns — Layered, Event-Driven, Microkernel, Microservices, Space-Based — each analyzed against a consistent set of six architecture characteristics.

## The Consistent Evaluation Framework

Every pattern in this report is scored against the same six characteristics, which is itself a useful checklist to apply to any architecture decision, not just these five patterns: **overall agility** (how quickly the system responds to changing requirements), **ease of deployment**, **testability**, **performance**, **scalability**, and **ease of development**. Rating one architecture option against a fixed set of characteristics — rather than describing patterns purely qualitatively — is a good habit for architecture decision records generally.

## 1. Layered (N-Tier) Architecture

The de facto default architecture, "closely matches the traditional IT communication and organizational structures found in most companies." Standard four layers: presentation, business, persistence, database (sometimes business+persistence merge into three layers; larger systems may split further into five or more).

- **Closed vs. open layers**: a *closed* layer means a request must pass through the layer immediately below it to reach anything further down (presentation -> business -> persistence -> database, no skipping). Marking specific layers **open** (allowed to be bypassed) is a deliberate escape hatch for cases like a shared/common services layer that many layers legitimately need direct access to — but doing this indiscriminately reintroduces the tight coupling the pattern exists to prevent, since "open" layers create hidden dependencies between layers that are supposed to be independently replaceable.
- **Failure mode without a formal architecture**: the report names the alternative explicitly — the **"big ball of mud" anti-pattern**, an unorganized pile of modules with unclear roles and relationships, that most codebases default toward without an explicit architectural discipline.
- **Characteristic profile**: this pattern's most commonly noted weaknesses are *not* development ease (which is high, since it's familiar) but **deployment, performance, and scalability** — every deployment typically requires redeploying the whole layered monolith even for a small change, and a request must traverse every layer, adding latency, with no way to scale one layer independently of the others.

## 2. Event-Driven Architecture

Two distinct topologies for coordinating asynchronous, decoupled components — worth distinguishing precisely since they solve different problems:

- **Mediator topology**: a central **event mediator** receives an *initial event*, knows the multi-step sequence required to fulfill it (including which steps can run in parallel), and emits individual *processing events* to event channels for **event processors** to handle — but the mediator itself contains no business logic, only orchestration knowledge. Implementation options range from lightweight (Spring Integration, Apache Camel, Mule Enterprise Service Bus, or ESB) to heavyweight process orchestration (Business Process Execution Language, or BPEL, engines; full Business Process Manager, or BPM, products for workflows involving human steps). Explicit warning: mismatching implementation weight to actual complexity — using a full BPM engine for simple routing, or a lightweight integration hub for genuinely complex multi-step orchestration requiring human interaction — "is a recipe for failure" in both directions.
- **Broker topology**: no central mediator; each event processor receives an event, does its work, and publishes a *new* event describing what it did, picked up by whichever other processors are interested — described memorably as a relay race, where each processor is "done" with an event once it hands it off. Useful specifically when the process is simple enough not to need central orchestration.
- **Shared consideration for both topologies**: **no atomic transactions across event processors** — because processing is distributed and asynchronous, a single business operation split across multiple event processors cannot be wrapped in one transaction. If a design requires that kind of cross-processor atomicity, event-driven architecture is explicitly flagged as the wrong pattern choice, not something to force-fit with extra tooling.
- **Characteristic profile**: high agility, deployability, performance, and scalability (processors are independently deployable/scalable); but **low testability and ease of development**, because asynchronous flows require specialized test tooling and rigorous, versioned event-contract discipline from day one.

## 3. Microkernel (Plug-in) Architecture

Two component types: a minimal **core system** (only what's needed to make the system operational) and independent **plug-in modules** that extend it, connected via a **plug-in registry** tracking each plug-in's name, data contract, and access protocol. Canonical examples: the Eclipse Integrated Development Environment (IDE), web browsers with extensions — and, notably, the report gives a genuinely useful **business-application** example: an insurance claims processor where each U.S. state's distinct legal rules become a separate plug-in around a shared core claims-processing engine, avoiding the "big ball of mud" that a single monolithic rules engine handling every state's exceptions inevitably becomes.

- Plug-ins connect via OSGi (Open Service Gateway Initiative), messaging, web services, or direct in-process binding — the pattern itself is agnostic to the connection mechanism, only requiring plug-in independence from one another.
- **Explicit compositional note**: this pattern is commonly *embedded inside* another architecture rather than used as the whole system design — e.g., using microkernel/plug-in structure for one particularly volatile subsystem within an otherwise layered application. Worth remembering that these five patterns aren't mutually exclusive at the whole-system level; they can nest.
- **Characteristic profile**: high agility, deployability (plug-ins can often be hot-deployed), and testability (plug-ins mockable/testable in isolation), and — a point worth remembering — performance can be *good* specifically because unnecessary features can be entirely excluded from a given deployment (the report cites JBoss Application Server's plug-in trimming as an example). Weakest at **scalability** (typically implemented as a single deployable product, not a distributed system) and **ease of development** (contract versioning and plug-in registry design require real upfront discipline).

## 4. Microservices Architecture

Evolved from two distinct pain points, worth knowing as the historical justification: monolithic layered applications' slow "monthly big-bang" deployment cycles, and Service-Oriented Architecture (SOA)'s excessive complexity/cost/orchestration overhead. Microservices addresses both by keeping services simple (no heavyweight orchestration layer) while still achieving independent deployability.

Three named topologies:
- **Application Programming Interface (API) REST-based**: very fine-grained services (one or two modules each) exposed via a separate Representational State Transfer (REST) API layer — classic public cloud API pattern (the report's examples: Yahoo/Google/Amazon-style public web services).
- **Application REST-based**: a separate web-based UI layer remotely calls coarser-grained service components via REST — suited to small/medium business applications.
- **Centralized messaging**: like the application REST-based topology, but using a lightweight message broker (ActiveMQ, HornetQ) instead of REST for transport, adding queuing, async messaging, and better load balancing — the report is explicit that this **must not** be confused with SOA/"SOA-lite," because the broker here does *no* orchestration, transformation, or routing logic, purely transport.

**The central design challenge, stated precisely**: getting service-component **granularity** right. Too coarse and the benefits (independent deployability, scalability, testability) don't materialize. Too fine and you're forced into **inter-service orchestration**, which "will quickly turn your lean microservices architecture into a heavyweight service-oriented architecture" — exactly the complexity microservices was meant to escape. Diagnostic heuristics offered: if the UI/API layer has to orchestrate multiple service calls to satisfy one user request, or if services need to call each other to complete a single request, granularity or business-domain partitioning is wrong. Suggested fixes for avoiding inter-service coupling: let services independently query a **shared database** for data they need (rather than calling another service for it), and accept **deliberate code duplication** of small shared utility logic across services (explicitly framed as trading DRY — "Don't Repeat Yourself" — for genuine service independence, a conscious, named trade-off rather than an oversight).

- **Characteristic profile**: high agility, deployability, testability, scalability, and ease of development — the most broadly high-scoring pattern in this report's framework, *except* for **performance**, rated low, due to the inherent network-hop cost of a distributed architecture (any individual well-optimized implementation can still perform well; the *pattern* doesn't naturally favor it the way, say, the in-memory space-based pattern does).

## 5. Space-Based Architecture (a.k.a. Cloud Architecture)

Purpose-built to solve the **scalability funnel problem**: in a standard web/app/database three-tier request flow, the database is always the narrowest, hardest-to-scale point — scaling web and app servers just pushes the bottleneck down to the database, which is the most expensive and difficult tier to scale out. Space-based architecture removes the central database as a bottleneck entirely by keeping application data in **replicated in-memory data grids** distributed across dynamically-scaled **processing units**, with an optional async persistent store used for failover/durability rather than as the primary read/write path. Named after "tuple space" (distributed shared memory) — the author notes he prefers "space-based" over the common alternative name "cloud architecture" specifically because the pattern doesn't require actual cloud/Platform-as-a-Service (PaaS) hosting; it's equally implementable on local infrastructure. Representative products: GemFire, GigaSpaces, Oracle Coherence, IBM Object Grid.

Canonical use case: high-concurrency, highly variable-load systems like a live bidding/auction site, where processing units can be spun up and down dynamically as concurrent load fluctuates, with no fixed database ceiling.

- **Characteristic profile**: high agility, deployability, performance, and scalability (the primary reason to choose this pattern at all); low **testability** (reproducing extreme concurrent load in a test environment is itself expensive and slow) and low **ease of development** (in-memory data grid tooling has a real learning curve, and developers must actively avoid writing code that undermines the caching/replication model's performance guarantees).

## Choosing Between Patterns

The report's own explicit heuristic: identify your **primary architectural concern** first (e.g., scalability), then check which patterns score highest specifically on that characteristic (event-driven, microservices, and space-based all rate high on scalability; layered rates low). But it also explicitly warns that the scoring table is only one input — infrastructure support, team skill set, budget, deadlines, and application size all matter, and because architecture choice is expensive to reverse once implemented, the decision deserves this level of explicit, characteristic-by-characteristic justification rather than defaulting to whatever's familiar.

## Takeaways for a Senior Backend Java Developer

- The "closed vs. open layers" distinction is a precise, useful vocabulary upgrade over the vague "layered architecture" label most engineers use loosely — worth using this exact terminology when reviewing whether a proposed layer-skipping shortcut is a deliberate, scoped exception or an architecture violation.
- The microservices granularity diagnostic ("if the caller has to orchestrate multiple service calls, or services must call each other to complete one request, granularity is wrong") is a genuinely actionable code-review heuristic, more concrete than generic "services should be loosely coupled" advice.
- The explicit DRY-vs-service-independence trade-off in microservices is worth citing directly when a team debates whether to extract a "shared library" for logic duplicated across two or three small services — the report's answer is that some duplication is often the *correct* trade against reintroducing coupling, not automatically bad practice.
- Space-based architecture is the least commonly discussed of these five patterns in most system-design interview prep material (compare `doc/references/System design/` for other titles in this folder) but is directly relevant background for understanding in-memory data grid products and any system explicitly designed to eliminate a database as the scaling bottleneck.
