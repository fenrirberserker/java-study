# Kafka: The Definitive Guide, 2nd Edition (Shapira, Palino, Sivaram, Petty — O'Reilly, 2021)

The authoritative, most mechanically detailed of the four books — written substantially by Kafka's original engineers and maintainers. Its standout contributions over the other three: the controller/replication protocol in full detail, the KRaft (Raft-based controller) migration away from ZooKeeper, the idempotent-producer and transactional-producer mechanisms underlying exactly-once semantics, precise consumer poll-loop internals, and a dedicated Kafka Connect chapter. This is the primary source for the "durability/delivery guarantees" and "operational concerns" depth in `doc/Study.md`'s Kafka section.

## Controller election and cluster metadata: ZooKeeper mode vs. KRaft

**What**: The **controller** is the single broker responsible for cluster-wide metadata management — electing partition leaders, creating/deleting topics, reassigning replicas — coordinated through one of two mechanisms depending on Kafka version/configuration.

**Why**: Every partition needs exactly one leader at a time; without a single coordinating authority, two brokers could each believe they're entitled to elect a leader, producing a split-brain cluster. Kafka's own architecture evolved because the original mechanism didn't scale to very large partition counts.

**How — legacy ZooKeeper-based controller**: brokers race to create an *ephemeral znode* at a well-known ZooKeeper path; the first to succeed becomes controller, and every other broker sets a watch on that znode so it's notified the moment the controller disappears (crash, network partition, or a garbage collection pause long enough to miss ZooKeeper heartbeats). Each election increments a **controller epoch** number; brokers ignore any message carrying an older epoch than the one they've already seen — this is how Kafka fences a "zombie" controller that resumes sending stale commands after a long pause. On startup, the controller must read the *entire* replica state map from ZooKeeper before it can manage the cluster — in clusters with very large partition counts this reload can take seconds, and it recurs on every controller failover.

**How — KRaft (the current default)**: Kafka replaced the ZooKeeper-based controller with a **Raft-based controller quorum** (KIP-500/KIP-595/KIP-631), first previewed in Kafka 2.8 and production-ready starting with Kafka 3.0. All cluster metadata (topics, partitions, ISRs, configuration — everything formerly stored in ZooKeeper) is represented as a Kafka-style replicated log of metadata events, managed by a small quorum of controller nodes that elect their own leader (the **active controller**) using the Raft consensus algorithm, with no external system required. Brokers no longer have metadata pushed to them; instead they **fetch** metadata updates from the active controller via a `MetadataFetch` API and persist it to local disk, so a broker restart doesn't require a full metadata reload from a remote system. Controller failover is much faster because every controller in the quorum already tracks the latest metadata state as a hot standby, rather than needing to reload it after being elected. As of Kafka 4.0 (2024), ZooKeeper support was removed entirely — KRaft is not just the default but the only supported mode in current Kafka. When working with any Kafka cluster today, assume KRaft unless it's explicitly a legacy deployment.

**Practical implication**: operationally, this means modern Kafka clusters don't run or depend on a separate ZooKeeper ensemble at all — one fewer distributed system to deploy, secure, and reason about failure modes for, directly addressing the operational complexity that motivated the redesign.

## Replication protocol detail

**What**: Each partition has one **leader replica** (handles all produce requests and, by default, all consume requests) and zero or more **follower replicas** (replicate from the leader; promoted to leader if the current leader fails).

**How reads-from-followers works** (KIP-392): by default, all consumer reads go to the leader. Setting `client.rack` on the consumer plus `replica.selector.class=RackAwareReplicaSelector` on the broker (default is `LeaderSelector`) lets a consumer read from the geographically/topologically nearest in-sync replica instead — reducing cross-datacenter network cost at the expense of code complexity elsewhere (a replica lagging the leader can serve slightly stale reads). A custom `ReplicaSelector` implementation is also pluggable for other selection policies.

## The idempotent producer

**What**: Setting `enable.idempotence=true` makes the producer attach a unique **Producer ID (PID)** and a per-partition, monotonically increasing **sequence number** to every message, letting brokers detect and silently reject duplicate sends caused by the producer's own retry logic.

**Why**: With plain `acks=all` and retries enabled, a broker can persist a message and then fail before its acknowledgment reaches the producer; the producer, seeing a timeout, resends — producing a duplicate the consumer has no way to detect on its own. The idempotent producer closes exactly this gap (and only this gap — see limits below).

**How**: the broker tracks the last five sequence numbers per partition per producer (bounding this by capping `max.inflight.requests.per.connection` at 5, the idempotent producer's supported maximum). A message with an already-seen `(PID, sequence)` pair is rejected as a duplicate — logged and reflected in metrics, not surfaced as an application exception. An unexpectedly high incoming sequence number (a gap) produces an "out of order sequence" error, which typically indicates messages were lost in transit and is worth investigating rather than ignoring. Producer state survives broker failover: the leader keeps the last-five-sequences state in memory, followers replicate that in-memory state as they replicate messages, and the state is periodically snapshotted to disk (and rebuilt from the log's own record headers if a snapshot is stale) so a promoted follower can continue validating sequences without a gap. State is retained for `transactional.id.expiration.ms` (7 days default) after a producer goes idle — creating many short-lived idempotent/transactional producer instances at high churn can leak broker memory (a concrete number from the book: three new IDs/second sustained for a week ≈ 1.8 million producer-state entries, ≈ 5 GB RAM) — the fix is reusing a small number of long-lived producers, or lowering the expiration for workloads (e.g., Function-as-a-Service) that can't avoid churn.

**Limits**: the idempotent producer only de-duplicates retries **it itself initiated** — calling `producer.send()` twice with the same logical record is indistinguishable from two different records, and two separate producer instances (e.g., two application replicas) sending the same data are not deduplicated against each other either.

## Transactions: the actual protocol

**What**: A **transactional producer** (configured with a stable `transactional.id` that survives application restarts) can atomically write to multiple partitions and, when paired with a consumer's `sendOffsetsToTransaction()`, also atomically commit its input offsets alongside its output writes — making the whole consume-process-produce cycle atomic.

**Why**: Kafka Streams needs this to guarantee exactly-once results for stateful stream processing (aggregations, joins): without atomicity between "commit my consumed offset" and "publish my output," a crash between the two steps produces either a lost update or a reprocessed (duplicate) one.

**How — the two-phase-commit-like protocol**: modeled conceptually on Chandy-Lamport distributed snapshots, using "marker" control messages written into every partition involved in a transaction. Concretely:

1. `initTransactions()` registers the transactional ID with a **transaction coordinator** (a broker — each broker is coordinator for a subset of transactional IDs, the same way brokers are group coordinators for a subset of consumer groups) and bumps a **producer epoch**, fencing off any earlier "zombie" instance using the same transactional ID whose in-flight transaction gets aborted.
2. `beginTransaction()` is purely a client-side flag — the coordinator doesn't know yet.
3. As the producer sends to each new partition, it sends `AddPartitionsToTxnRequest`, recorded in the internal `__transaction_state` log — this is step 1 of the algorithm: *log the existence of an ongoing transaction and which partitions are involved*.
4. `sendOffsetsToTransaction()` (called before committing) sends consumed offsets plus the consumer group ID to the coordinator, which forwards them to the group coordinator to commit as it normally would.
5. `commitTransaction()`/`abortTransaction()` sends `EndTransactionRequest`. The coordinator logs the **intent** to commit/abort — step 2: *once logged, the outcome is fixed; recovery after a coordinator crash resumes from this log entry rather than re-deciding*. It then writes commit/abort **markers to every partition** involved (step 3), and finally logs completion (step 4). If the coordinator crashes mid-sequence, a newly elected coordinator resumes from the logged intent rather than losing the decision.
6. A transaction not committed/aborted within `transaction.timeout.ms` is auto-aborted by the coordinator.

**Zombie fencing beyond the producer epoch** (KIP-447, Kafka 2.5+): before 2.5, safe zombie fencing required statically mapping each transactional ID to a fixed set of partitions, so a restarted instance always reused the same transactional ID for the same partitions. KIP-447 instead lets the coordinator use **consumer group generation** (passed via `sendOffsetsToTransaction`) to recognize that a producer belongs to an older generation of the consumer group and fence it — avoiding the earlier requirement to spin up a same-named transactional producer purely to fence a zombie.

**Isolation levels and performance**: a `read_committed` consumer never returns records from a still-open transaction (the broker withholds them from fetch responses — the consumer doesn't buffer and filter client-side, so there's no consumer-side throughput cost). Consumer-visible latency does increase with the interval between transaction commits, since records are invisible until their transaction's commit marker lands. Producer-side overhead (one-time ID registration, per-partition registration, and one commit-marker write per transaction) is **independent of transaction size** — batching more messages per transaction amortizes this fixed cost, improving throughput.

**Scope**: transactions guarantee exactly-once *within Kafka* for the consume-process-produce pattern. They do not, by themselves, make an external side effect (e.g., a database write triggered by a consumed record) exactly-once — that still requires either an idempotent external write or a two-phase protocol with the external system.

## Consumer poll-loop mechanics

**What**: `KafkaConsumer.poll(Duration timeout)` is not just "fetch more records" — the *first* call to `poll()` on a new consumer also handles discovering the group coordinator, joining the group, and receiving a partition assignment, and any later rebalance (and its listener callbacks) is also processed **inside** a `poll()` call. This means almost any consumer-group-related exception surfaces as an exception thrown from `poll()`.

**Why a slow record processor triggers a rebalance**: Kafka detects a dead consumer two ways — missed heartbeats (`session.timeout.ms`, default 10s; controlled by a background heartbeat thread firing every `heartbeat.interval.ms`, conventionally one-third of the session timeout) and missed **polls** (`max.poll.interval.ms`, default 5 minutes). The heartbeat thread runs independently of the main processing thread, so a consumer whose main thread is stuck processing a slow batch can *still* be sending heartbeats and look "alive" by that measure alone — `max.poll.interval.ms` exists specifically as the backstop that catches this case: if the main thread doesn't call `poll()` again within that interval, the background thread sends a "leave group" request itself and stops heartbeating, forcing a rebalance. `max.poll.records` caps how many records a single `poll()` returns, which is the direct lever for keeping per-poll processing time predictable and under `max.poll.interval.ms` when processing is slow or variable per record.

**Other consumer tuning knobs worth knowing precisely**: `fetch.min.bytes` (broker waits for at least this many bytes before responding, reducing request/response chatter on low-traffic topics) paired with `fetch.max.wait.ms` (default 500ms — upper bound on that wait, so low-throughput topics don't add unbounded latency) and `fetch.max.bytes` (default 50MB cap on total response size, though a single oversized first batch is still returned in full so the consumer always makes progress) vs. the per-partition `max.partition.fetch.bytes` (1MB default — harder to reason about because you don't control how many partitions land in one response, so `fetch.max.bytes` is the generally recommended lever).

**Thread-safety rule**: a single `KafkaConsumer` instance is not thread-safe, and a single thread cannot run two consumers in the same group — the enforced pattern is one consumer per thread, with an `ExecutorService`-managed thread pool if you want multiple consumers reading a group in parallel within one application.

## Kafka Connect (architecture and operations)

**What**: A framework, bundled with Kafka core, standardizing data movement into/out of Kafka via pluggable **source connectors** (import) and **sink connectors** (export), run by **workers** that can operate standalone (single process, useful when a connector must run on a specific known machine, e.g. one that tails a local log file) or **distributed** (a cluster of workers identified by a shared `group.id`, coordinating and rebalancing connector tasks across themselves the same way a consumer group rebalances partitions).

**Why it belongs in the pipeline design conversation, not just as a tool**: Kafka's core value in a data pipeline is acting as a large, durable buffer that decouples producer and consumer timeliness requirements (a producer can write in real time while a batch consumer reads hourly, or vice versa) — Connect exists specifically to standardize the two most common pipeline shapes (Kafka ↔ one external system, or external system → Kafka → another external system) without every team re-deriving offset tracking, schema handling, and fault tolerance from scratch. Reliability requirements (at-least-once always achievable by Kafka alone; exactly-once achievable when the external system offers transactional writes or unique-key upserts) and format handling (pluggable **converters** — JSON built in; Avro/Protobuf/JSON Schema via Confluent Schema Registry) are Connect's main design surface.

**How — key worker configuration**: `bootstrap.servers`, `group.id` (workers sharing a `group.id` form one distributed Connect cluster), `plugin.path` (directories Connect scans for connector jars and their dependencies — the recommended way to add connectors, versus putting them directly on the classpath, which risks dependency conflicts), `key.converter`/`value.converter` (format for data as stored in Kafka), and `rest.host.name`/`rest.port` (workers expose a Representational State Transfer (REST) Application Programming Interface (API) for configuring and monitoring connectors — `curl http://host:8083/connector-plugins` lists what's available). A minimal file-source connector, defined purely through configuration and requiring no custom code:

```properties
name=local-file-source
connector.class=FileStreamSource
tasks.max=1
file=test.txt
topic=connect-test
```

**Transformations**: Kafka Connect's Single Message Transformation (SMT) feature handles lightweight in-flight reshaping (routing, filtering, field redaction, type conversion) as data passes through a connector. Joins and aggregations are explicitly out of scope for Connect and are Kafka Streams' job instead — this is the same DSL-vs-custom-logic boundary discussed in `kafka-streams-in-action.md`, one layer up the stack.

**Extract-Transform-Load (ETL) vs. Extract-Load-Transform (ELT) trade-off**: transforming data in the pipeline (ETL) saves downstream storage/compute but locks every consumer of that topic into the pipeline author's transformation choices — if a field is dropped in-flight, every downstream consumer permanently loses access to it without a pipeline rebuild and historical reprocessing. ELT (minimal in-flight transformation, raw data landed at the target, transformed there) maximizes downstream flexibility at the cost of shifting compute/storage burden to the target system. Kafka's one-to-many fan-out (one topic, many independent consumers) makes premature in-pipeline cleanup specifically risky, since it constrains every consumer, not just the one that requested the transform.

## Kafka Streams processing guarantees

`processing.guarantee=exactly_once_v2` (the modern name — `exactly_once_beta` in the version current when this book was written, `exactly_once` was the original but less efficient variant requiring more broker-side transaction coordinator load per task) enables Kafka Streams' internal use of the transactional producer/idempotent producer mechanisms described above, transparently to application code. The default is `at_least_once`. This chapter's window-type coverage (tumbling vs. hopping, aligned to clock boundaries vs. free-running from application start) matches and doesn't materially extend what `kafka-streams-in-action.md` already covers in more depth with worked examples — see that file for the mechanics.
