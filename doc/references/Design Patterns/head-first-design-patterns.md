# Head First Design Patterns (2nd Edition)

Source: Eric Freeman, Elisabeth Robson, Bert Bates, Kathy Sierra, *Head First Design Patterns* (O'Reilly, 2nd edition, 2014, 867 pages — large-format, illustration-heavy "Head First" layout, so page count does not reflect prose density). Sampled: full table of contents (13 chapters plus a "Leftover Patterns" appendix), and a detailed read of Chapter 1's introduction of the first two design principles via the running "SimUDuck" example (pages 47-51).

This book covers largely the same pattern catalog as `gang-of-four-design-patterns.md` and `dive-into-design-patterns.md`, teaching through extended, memorable narrative case studies (a duck simulator, Starbuzz Coffee, a pizza store franchise, a chocolate factory, a universal remote control, a home theater, a diner/pancake-house menu merger, a gumball machine, a DJ beat-making app) rather than abstract description. This reference captures the book's distinctive value: **the specific design-principle checklist it builds up chapter by chapter**, and **which pattern is taught through which memorable scenario** — useful as a fast recall aid, since the scenario names are what stick in memory long after the formal GoF definitions fade. Formal pattern intents are already catalogued precisely in `gang-of-four-design-patterns.md`; this file does not repeat them.

## The Design Principles Checklist (built up across chapters)

The book's structure is essentially a sequence of design principles, each motivated by a concrete failure scenario before the pattern that embodies it is introduced:

1. **Identify the aspects of your application that vary, and separate them from what stays the same** ("encapsulate what varies") — introduced via the SimUDuck problem: subclassing `Duck` for `fly()`/`quack()` behavior breaks down because not all ducks fly or quack the same way, and Java interfaces alone don't allow code reuse across unrelated subclasses. This is the seed principle behind the **Strategy pattern**: behaviors (`FlyBehavior`, `QuackBehavior`) are pulled into their own class hierarchies, and a `Duck` is *composed* with a behavior object rather than inheriting one.
2. **Program to an interface, not an implementation** — restated as "program to a supertype" in the book's own words; the immediate follow-on from principle 1, since separating what varies only helps if client code depends on the abstract behavior type, not a concrete implementation.
3. **Favor composition over inheritance** — "HAS-A can be better than IS-A." Composing a `Duck` with behavior objects, versus inheriting fixed behavior, is what makes runtime behavior swapping possible (`duck.setFlyBehavior(new FlyRocketPowered())`).
4. **Strive for loosely coupled designs between objects that interact** — introduced with the **Observer Pattern** (weather station example): publishers (subjects) and subscribers (observers) know each other only through a thin interface, so either side can change independently, and new observer types can be added without touching the subject.
5. **Classes should be open for extension, but closed for modification** (Open-Closed Principle) — introduced with the **Decorator Pattern** (Starbuzz Coffee beverage/condiment pricing): rather than editing a `Beverage` class every time a new condiment is added, condiments *wrap* a beverage object, each adding their own cost/description while implementing the same supertype — new condiments require zero changes to existing classes. Explicit caveat given in the book (also echoed in `dive-into-design-patterns.md`): applying Open-Closed everywhere is wasteful and adds needless complexity/indirection; apply it specifically to the parts of a design most likely to change.
6. **Depend upon abstractions. Do not depend upon concrete classes** (Dependency Inversion Principle) — introduced with the **Factory Method** and **Abstract Factory patterns** (pizza store franchise example): a `PizzaStore` that directly `new`s concrete `NYStyleCheesePizza`/`ChicagoStyleCheesePizza` objects is tightly coupled to every regional variant; deferring instantiation to subclasses (Factory Method) or to a family-of-related-objects factory (Abstract Factory, for consistent ingredient families per region) removes that coupling. The book gives concrete corollary guidelines for following this principle: no variable should hold a reference to a concrete class, no class should derive from a concrete class, no method should override an implemented method of any of its base classes — stated as aspirational "guidelines to strive for" rather than absolute rules, since some concrete-class dependency (e.g., instantiating basic value/data types) is unavoidable in practice.
7. **A class should have only one reason to change** (Single Responsibility Principle) — introduced in the Iterator/Composite chapter (diner/pancake-house menu merger): separating iteration responsibility (Iterator) from collection-management responsibility keeps a `Menu`-like class from having to change both when its storage structure changes *and* when its traversal needs change.
8. **The Principle of Least Knowledge** ("Don't talk to strangers") — introduced with the **Facade Pattern** (home theater example): an object should only invoke methods on itself, objects passed as parameters to it, objects it creates, and its direct component objects — not on objects returned by calls to other methods, chains that reach deep into other objects' internals. Fewer classes an object depends on directly means fewer changes ripple through the system when other classes change. Explicit caveat: over-applying this principle produces excessive "middle-man" wrapper classes, trading coupling for complexity — a real trade-off, not a free win.
9. **The Hollywood Principle** ("Don't call us, we'll call you") — introduced with the **Template Method Pattern** (caffeinated-beverage recipe example: `CaffeineBeverage.prepareRecipe()` is a fixed algorithm skeleton with `brew()`/`addCondiments()` steps deferred to `Coffee`/`Tea` subclasses). Framed as a specific instance of Dependency Inversion applied to control flow: high-level components call down into low-level components only through well-defined hook points, rather than low-level components calling up into high-level ones directly — preventing low-level code from creating dependencies back up the hierarchy. The book connects this explicitly to frameworks generally (a framework's fixed control flow calling your registered hooks) — the same inversion-of-control idea discussed from a different angle in `dive-into-design-patterns.md`'s Erich Gamma quote.

## Patterns Taught Through Named Scenarios (recall aid)

| Pattern | Teaching scenario | Core lesson |
|---|---|---|
| Strategy | SimUDuck duck simulator | Compose interchangeable behavior objects instead of inheriting fixed behavior |
| Observer | Weather monitoring station | Subject notifies a dynamic list of subscribers on state change; contrasted with Java's now-deprecated built-in `Observable` |
| Decorator | Starbuzz Coffee beverage pricing | Wrap objects to add responsibilities dynamically; same shape as Java I/O's `InputStream`/`FilterInputStream` wrapping |
| Factory Method | Pizza store regional franchises | Defer object instantiation to a subclass-overridden factory method |
| Abstract Factory | Pizza store regional ingredient families | Produce a whole family of related objects (ingredients) guaranteed to be mutually compatible |
| Singleton | Chocolate factory / Boiler | The classic lazy-initialization-with-synchronization walkthrough, including the double-checked-locking refinement (also covered from the OCP exam's angle in `doc/references/Java/ocp-java-se8-programmer-2.md`) |
| Command | Universal remote control | Encapsulate a request as an object to support parameterized invocation, queuing, logging, and undo; shows a macro-command composing multiple commands, and a modernized version using Java 8 lambdas/method references in place of many small command classes |
| Adapter | Duck-to-Turkey adapter, Enumeration-to-Iterator | Convert one interface to another expected interface; distinguishes object adapters (composition-based) from class adapters (inheritance-based, only possible in languages with multiple inheritance) |
| Facade | Home theater (amplifier, projector, screen, lights, popper) | Provide one simplified interface over a complex subsystem, without hiding the subsystem's full interface from clients who still need it directly |
| Template Method | Caffeinated beverage recipes (coffee/tea), `Collections.sort()`/`Comparable` | Fixed algorithm skeleton with deferred steps; connects the pattern to `java.util.Arrays.sort`'s use of `compareTo()` as a live Java Development Kit (JDK) example |
| Iterator | Diner (`ArrayList`-backed) and pancake house (`array`-backed) menus, merged | Uniform traversal over incompatible underlying collection representations, without exposing that representation |
| Composite | Merged diner/pancake-house/café menu hierarchy (menus containing menus) | Treat individual items and composite groups of items uniformly via a shared component interface; paired directly with Iterator for traversing tree structures |
| State | Gumball machine game logic | Encapsulate per-state behavior in state objects instead of a sprawling conditional; contrasted directly against Strategy, since the two patterns have near-identical class diagrams but opposite intents (State: an object's behavior changes as its internal state changes, driven from within; Strategy: a client chooses/injects an interchangeable algorithm from outside) |
| Proxy | Gumball machine remote monitoring (Java Remote Method Invocation, or RMI), lazy-loaded CD-cover images, a dynamic-proxy-based matchmaking service | Provide a stand-in controlling access to a real object — covers remote proxies (network-transparent stand-ins), virtual proxies (lazy/expensive object creation), and protection proxies (Java's `java.lang.reflect.Proxy` dynamic proxy mechanism) as three distinct variants of the same pattern |
| Model-View-Controller (MVC) | DJ beat-making application, adapted to a Model 2 web architecture | Presented as a **compound pattern** — MVC is not one pattern but Observer (view observes model), Strategy (controller as the view's interchangeable behavior), and Composite (nested view components) working together; a good worked example of how real architectures combine multiple patterns rather than applying them in isolation |

The appendix ("Leftover Patterns") gives brief, lighter-weight coverage of **Bridge, Builder, Chain of Responsibility, Flyweight, Interpreter, Mediator, Memento, Prototype,** and **Visitor** — patterns judged less central to everyday use but included for catalog completeness; formal intents for all of these are in `gang-of-four-design-patterns.md`.

## State vs. Strategy (a frequently confused pair, worth being precise about)

Both patterns produce nearly identical Unified Modeling Language (UML) class diagrams (a context object holding a reference to an interchangeable interface implementation), which is exactly why the book pairs them for direct contrast:
- **Strategy**: the client explicitly selects and injects a specific algorithm/behavior into a context object from the outside — the context doesn't drive the choice itself, and typically doesn't switch strategies as a normal part of its own operation.
- **State**: the context's *own* current state object is responsible for deciding the next state transition, often triggering the change from within itself as part of normal operation — the client doesn't typically pick states directly; the object appears to change its class/behavior as it moves through its lifecycle.

This distinction ("who decides, and when") is a good one-line test to apply whenever two designs look structurally identical but are being called different pattern names.

## Takeaways for a Senior Backend Java Developer

- The State-vs-Strategy distinction ("does the object drive its own transitions, or does an external client inject a fixed choice") is a genuinely useful, precise test worth having ready — the two patterns are commonly confused specifically because their class diagrams are nearly identical.
- The Principle of Least Knowledge's explicit "don't over-apply this, you'll create a wrapper-class explosion" caveat is a good citation when reviewing code that has added a facade/wrapper purely to avoid one method chain, at the cost of an extra indirection layer with no other benefit.
- The Template Method chapter's explicit connection to `Comparable`/`Arrays.sort()` and the Hollywood Principle's connection to framework-style inversion of control are good concrete, already-in-the-JDK examples to reach for when explaining either concept to someone unfamiliar with formal pattern names.
- The MVC-as-compound-pattern treatment (Observer + Strategy + Composite) is a valuable reminder that most real architecture doesn't apply patterns in isolation — recognizing which combination of patterns a familiar architecture (MVC, or any observer-plus-pluggable-behavior system) is built from deepens understanding of both the architecture and the underlying patterns simultaneously.
