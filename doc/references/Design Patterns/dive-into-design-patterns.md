# Dive Into Design Patterns (Refactoring.Guru)

Source: Alexander Shvets, *Dive Into Design Patterns* (Refactoring.Guru, v2023-2.46, 411 pages). Sampled: full table of contents, and detailed reads of "Features of Good Design" (pages 34-38) and the complete SOLID principles chapter (pages 53-71).

This is a modern (post-GoF), example-driven treatment of the same 22 classic patterns covered in `doc/references/Design Patterns/gang-of-four-design-patterns.md` — same catalog (this edition presents 22, having folded Interpreter out of scope), pseudocode instead of C++/Smalltalk, and heavier use of before/after worked examples. Its distinctive, genuinely additive content versus the GoF original is the **SOLID principles chapter**, which the original 1994 book predates (SOLID was named as an acronym by Robert C. Martin in the early 2000s, though several of its constituent principles — including Liskov Substitution — predate the acronym). This reference focuses on that SOLID content plus the book's framing of code reuse and extensibility, and does not re-list the 22 patterns' intents (already catalogued precisely in `gang-of-four-design-patterns.md`).

## Levels of Code Reuse (Erich Gamma's framing, quoted in the book)

A three-level hierarchy worth having as vocabulary: **classes** (the lowest level — reusing individual class libraries, containers, and small class "teams" like a container plus its iterator) -> **design patterns** (a middle level — smaller and more abstract than a framework; a pattern only describes how a handful of classes can relate to and interact, independent of concrete code) -> **frameworks** (the highest level — distills a whole set of design decisions into concrete classes and their relationships, typically hooked into via subclassing, using **inversion of control**, the "Hollywood principle": "don't call us, we'll call you." JUnit, with its `Test`/`TestCase`/`TestSuite` classes and defined relationships, is offered as the "hello world" of frameworks). The key trade-off stated explicitly: patterns offer reuse that is **less risky** than building or adopting a framework — building a framework is a large, high-risk investment, while a pattern lets you reuse a design idea without committing to concrete shared code.

## SOLID Principles

### Single Responsibility Principle (SRP)
"A class should have just one reason to change." The goal is managing complexity as a codebase grows — a class handling multiple unrelated responsibilities must be touched (and risks breaking) every time *any* of those responsibilities changes, even ones unrelated to the change being made. Worked example: an `Employee` class that both manages employee data *and* formats timesheet reports has two independent reasons to change; extracting the reporting behavior into its own class removes one of them.

### Open/Closed Principle (OCP)
"Classes should be open for extension but closed for modification." A class is *open* if it can be extended (subclassed, have new methods/fields added) and *closed* if its interface is finalized and won't change under its existing clients. The point: once a class is developed, tested, and depended upon elsewhere, editing its source directly is risky — extending it (subclassing, or via a pattern like Strategy) achieves new behavior without touching or re-testing existing client code. Explicit caveat: this principle is about **adding new behavior**, not about fixing bugs — a genuine defect should be fixed in place, not patched around via a subclass ("a child class shouldn't be responsible for the parent's issues"). Worked example: hard-coded shipping-cost calculation logic inside an `Order` class is refactored by extracting each shipping method into its own class behind a common `Shipping` interface (the Strategy pattern) — adding a new shipping method no longer requires touching `Order` at all.

### Liskov Substitution Principle (LSP)
"When extending a class, you should be able to pass objects of the subclass in place of objects of the parent class without breaking the client code." Named for Barbara Liskov (1987). Unlike the other SOLID principles, LSP has a **precise, checkable rule set** for subclass method signatures and behavior — worth having memorized as a checklist since it's a common source of subtle inheritance bugs:

1. **Parameter types must match or be more abstract (contravariant)** than the superclass method's parameter types — a subclass method that *narrows* an accepted parameter type (e.g., overriding `feed(Animal)` with `feed(BengalCat)`) breaks client code that expects to pass any `Animal`.
2. **Return types must match or be a subtype (covariant)** of the superclass method's return type — the inverse rule from parameters; a subclass method returning a *broader* type than what callers expect (e.g., overriding `buyCat(): Cat` with `buyCat(): Animal`) breaks client code that only knows how to work with `Cat`.
3. **A subclass method shouldn't throw exception types the base method doesn't declare/expect** — client `try`/`catch` blocks are written against the base method's declared exceptions; an unexpected exception type from an override can slip past them uncaught.
4. **A subclass shouldn't strengthen preconditions** — e.g., a base method accepting any `int` but an override throwing on negative values breaks callers who legitimately passed negative numbers to the original.
5. **A subclass shouldn't weaken postconditions** — e.g., a base method guaranteed to close a database connection before returning, but an override that leaves it open (even for a good reason, like connection reuse), breaks callers relying on the original guarantee.
6. **Invariants of the superclass must be preserved** — described as the least formal, easiest-to-violate rule, since invariants are often implicit (embedded in unit tests or client expectations) rather than explicitly documented. The book's stated safest strategy: extend a class primarily by *adding* new fields/methods rather than altering existing members' behavior.
7. **A subclass shouldn't be able to change the superclass's private field values** — a concern mainly in languages with weak/no access-control enforcement (reflection-based access, or dynamically typed languages with no private-field protection at all) rather than in a language like Java with genuine access control.

Worked example: a `ReadOnlyDocument`/`Document` hierarchy where a subclass throws on `save()` (a strengthened restriction the base type's contract didn't have) violates LSP; the fix is to invert the hierarchy so `ReadOnlyDocument` becomes the base class and a `WritableDocument` subclass *adds* the `save()` capability rather than removing it — a general pattern worth internalizing: **when a subclass wants to remove or restrict base behavior rather than add to it, the hierarchy is usually inverted from how it should be.**

### Interface Segregation Principle (ISP)
"Clients shouldn't be forced to depend on methods they do not use." Large ("fat") interfaces should be broken into narrower, more specific ones, so a class only has to implement what it actually needs — a change to one method of a bloated interface otherwise risks breaking every implementer, including ones that never used that method. Worked example: a cloud-provider integration library initially modeled around Amazon's full feature set breaks down once a second provider with a narrower feature set needs to implement the same interface; splitting the interface into smaller, focused interfaces lets each provider implement only the subset that applies to it. Explicit caveat against overuse, same spirit as the OCP guide's design-pattern warning: don't keep subdividing an already-specific interface — more interfaces means more design complexity, so balance is needed.

### Dependency Inversion Principle (DIP)
"High-level classes shouldn't depend on low-level classes. Both should depend on abstractions. Abstractions shouldn't depend on details. Details should depend on abstractions." Distinguishes **low-level classes** (basic operations: disk I/O, network transfer, database connections) from **high-level classes** (business logic that orchestrates low-level operations). The common failure mode: low-level classes get built first (since a prototype's low-level capabilities are often built before the business logic that will use them), and high-level business logic ends up directly dependent on those concrete low-level classes. DIP's fix is a three-step inversion: (1) define interfaces for the low-level operations the high-level class needs, phrased in business terms (e.g., `openReport(file)` rather than `openFile`/`readBytes`/`closeFile`); (2) make the high-level class depend on that interface instead of the concrete low-level class; (3) have the low-level class implement that interface — which means the low-level class now depends on an abstraction defined by the business layer, **reversing the original dependency direction**. Noted to often be applied together with the Open/Closed Principle: once high-level code depends only on an interface, low-level implementations can be extended/swapped without touching the high-level code at all.

**Note on terminology**: Dependency Inversion (the structural principle above) is frequently confused with **Dependency Injection** (the specific technique of supplying an object's dependencies from outside rather than having it construct them itself, typically via constructor/setter injection or a framework like Spring — see `doc/references/Spring/`). Dependency Injection is one common *mechanism* for achieving code that already follows Dependency Inversion; the two terms are related but not synonymous, and are worth being precise about in an interview.

## Takeaways for a Senior Backend Java Developer

- The Liskov Substitution checklist (parameter contravariance, return-type covariance, exception-type compatibility, precondition/postcondition preservation, invariant preservation) is the single most practically useful piece of this book for day-to-day code review — most "this override technically compiles but breaks callers" bugs trace back to violating one of these seven rules, and Java's own type system statically enforces some of them (parameter/return type compatibility) but not others (behavioral pre/postcondition and invariant preservation, which require manual discipline).
- The Interface Segregation Principle is a direct, practical justification for the widespread Java convention of small, focused interfaces (`Runnable`, `Comparable`, `AutoCloseable`) over large multi-purpose ones — worth citing explicitly when reviewing a proposed interface that's accumulating unrelated methods.
- Being precise about "Dependency Inversion is a principle; Dependency Injection is a technique that helps satisfy it" is a good interview-clarity signal — many developers use the terms interchangeably, and being able to draw the distinction crisply demonstrates real understanding rather than pattern-matched vocabulary.
- The three-level reuse hierarchy (classes -> patterns -> frameworks, patterns being lower-risk than framework adoption) is a useful way to frame "should we build a shared internal framework for this, or is a documented pattern/convention enough" discussions with a team.
